# ADR-001: Python Tooling via uv

Status: Accepted
Date: 2026-09-03

## Context

The CRIBA, SUPRA, and THEKEY projects require a reproducible Python environment.
Multiple versions of Python and project dependencies must coexist without
contaminating the global environment.

## Decision

Use `uv` as the package and environment manager for all Python projects.
Each project's dependencies are declared in `pyproject.toml` and installed by
`uv sync --all-extras --locked` using the checked-in `uv.lock`.

## Consequence

- Tool versions are pinned per-project (e.g., ruff 0.16.5 for CRIBA).
- No global Python packages are installed via pip.
- `uv.lock` files guarantee reproducible installs.

## Alternatives Considered

- **pip + virtualenv**: manual management, no lockfile, slower resolution.
- **poetry**: heavier convention, different lock format.
- **conda**: heavier, not aligned with project CI.

# ADR-002: Security Scanner Strategy

Status: Accepted
Date: 2026-09-03

## Context

BLACKFORGE and the security pipeline require static analysis, secret detection,
SBOM generation, and vulnerability scanning.

## Decision

Install a layered set of scanners:

- **Semgrep** — code-level static analysis (multi-language).
- **Bandit** — Python-specific security checks.
- **Gitleaks** — secret detection in git history.
- **Trivy** — filesystem vulnerability + SBOM scanning.
- **OSV-Scanner** — dependency vulnerability checking against OSV.
- **Syft** — SBOM generation.
- **Grype** — vulnerability scanning against SBOMs.
- **pip-audit** — Python dependency audit from uv.lock.

Each tool runs independently; results are NOT piped into a central aggregator
in this phase. Adapters will be built in a future phase if BLACKFORGE needs
unified reporting.

## Consequence

- Each scanner produces its own output format.
- Tools are installed per-project (Python) or system-wide (winget).
- CI already has Trivy and dependency-audit steps; these are reinforced locally.

## Alternatives Considered

- **Central aggregator (e.g., DefectDojo)**: requires server setup and is out
  of scope for the local-first constraint.
- **Single monolithic scanner**: no single tool covers all categories.

# ADR-003: Pre-commit Hooks

Status: Accepted
Date: 2026-09-03

## Context

Projects need fast pre-commit validation without slowing down developer workflow.

## Decision

Add `.pre-commit-config.yaml` to each project with:
- **ruff** (check + format) — the linter/formatter already used.
- **pre-commit-hooks** — trailing whitespace, YAML/TOML validity, large file check.
- **gitleaks** (local hook) — secret detection on commit.

## Consequence

- Hooks run in seconds; no 30-minute suites.
- Each project pins its own ruff version.
- `.env.example` templates are not committed (secret-free).

## Alternatives Considered

- **No pre-commit**: relies on CI only; slower feedback loop.
- **Full pre-commit suite (mypy, pytest)**: too slow for every commit.
