- pipeline_action representa la acción interna del pipeline:
  - PROTOTIPAR
  - DIVERGIR

- recommended_status representa una decisión de negocio y debe pertenecer

  - ADOPTAR
  - AMPLIAR PRUEBA
  - ABANDONAR
  - ARCHIVAR PARA RECOMBINAR

Mientras no exista una regla de negocio explícita y probada que justifique
ADOPTAR:

- len(families) >= 4:
  - pipeline_action = "PROTOTIPAR"
  - recommended_status = "AMPLIAR PRUEBA"

- len(families) < 4:
  - pipeline_action = "DIVERGIR"
  - recommended_status = "AMPLIAR PRUEBA"

1. REGLAS ANTI-PATRÓN NO NEGOCIABLES
======================================================================

1.1 PROHIBIDO DECLARAR EL PROYECTO COMPLETADO SIN COMMITS

No escribas PROJECT_COMPLETED si no existe al menos un commit Git atómico por
cada bloque material de cambio.

Cada commit debe:

- corresponder a una unidad coherente;
- pasar sus pruebas asociadas;
- usar Conventional Commits;
- describir exactamente qué cambió y por qué;
- evitar mensajes genéricos como “mejoras varias”.

1.2 PROHIBIDO INVENTAR EL BASELINE

No afirmes:

- “128 tests verdes”;
- “suite verde”;
- “cobertura X%”;
- “mypy limpio”;
- “sin secretos”;

sin haberlo comprobado en esta sesión y registrado con comando y resultado.

El mensaje del commit inicial debe construirse con los resultados realmente
observados.

1.3 PROHIBIDO REGENERAR GOLDEN MASTERS SIN RATIFICACIÓN

Si un golden master, snapshot o fixture de referencia falla después de cambiar
el código que verifica:

1. detente;
2. identifica el diff exacto;
3. separa cambios esperados de cambios accidentales;
4. documenta la causa;
5. no regeneres el golden;
6. solicita decisión humana.

No uses como única evidencia la salida generada por el mismo código recién
modificado.

1.4 PROHIBIDO INVENTAR EQUIVALENCIAS SEMÁNTICAS

No renombres ni mapees valores de enums o contratos suponiendo equivalencia.

Ejemplo prohibido:

PROTOTIPAR -> ADOPTAR

ante una discrepancia no ratificada:

- no modifiques;
- documenta;
- crea estado bloqueado;
- solicita decisión humana.

La separación pipeline_action / recommended_status ya está ratificada y sí
debe implementarse o verificarse.

1.5 LOS TESTS PROPIOS NO SON EVIDENCIA INDEPENDIENTE SUFICIENTE

“Todos los tests pasan” no basta cuando tú mismo modificaste simultáneamente:

- implementación;
- tests;
- fixtures;
- snapshots;
- golden masters.

Para cambios importantes exige además, según corresponda:

- comparación contra contrato previo;
- prueba adversarial;
- prueba de regresión;
- ejecución headless real;
- diff semántico;
- compatibilidad hacia atrás;
- evidencia independiente existente.

1.6 PROHIBIDO SILENCIAR ERRORES

No uses para conseguir verde:

- except Exception sin re-raise justificado;
- # type: ignore generalizado;
- noqa masivo;
- xfail sin causa;
- skip permanente;
- reducción artificial de asserts;
- ampliación arbitraria de tolerancias;
- eliminación de tests;
- modificación de expected values sin evidencia.

1.7 NO TRABAJAR SOBRE DOS AGENTES A LA VEZ

No asumas que Hermes, Codex u otro agente puede modificar simultáneamente este
workspace. Trabaja como único escritor.

1.8 NO HACER PUSH NI PUBLICAR

Esta misión es de hardening local.

No ejecutes:

- git push;
- gh repo create;
- publicación de releases;
- cambios remotos;

salvo instrucción humana explícita posterior.

- termina con:

HUMAN_DECISION_REQUIRED

Después de emitir una señal terminal:

- no ejecutes más herramientas;
- no añadas verificaciones;
- no escribas texto adicional.

12. CRITERIO ESTRICTO PARA PROJECT_COMPLETED
======================================================================

Solo escribe PROJECT_COMPLETED si:

- FASE 0–5 completadas;
- FASE 6 ejecutada hasta un punto razonable o documentada;
- todos los cambios tienen commits atómicos;
- working tree limpio o cambios pendientes explícitamente justificados;
- suite completa verde;
- cobertura registrada;
- ramas críticas cubiertas;
- mypy strict verde en código propio;
- no existen goldens regenerados sin ratificación;
- contratos JSON compatibles;
- pipeline_action y recommended_status separados;
- value_score intacto y protegido;
- benchmark registrado;
- docs actualizadas;
- HANDOFF actualizado;
- RESUME_NEXT_SESSION creado;
- no hay decisión humana bloqueante;
- .autoregen/project_completed.json es válido.

Si queda trabajo técnico no bloqueante pero el contexto está agotándose:

- no declares completo;
- usa CONTEXT_REGENERATION_REQUIRED.

Si aparece un conflicto semántico o de contrato:

- no lo resuelvas por inferencia;
- usa HUMAN_DECISION_REQUIRED.

======================================================================
13. PRIMERA RESPUESTA ESPERADA
======================================================================

Empieza indicando únicamente:

1. ruta confirmada;
2. existencia de .git;
3. estado inicial del árbol;
4. comando de baseline que vas a ejecutar;
5. confirmación de que no asumirás el número de tests;
6. confirmación de que no regenerarás goldens sin ratificación;
7. confirmación de que no harás push.

Después comienza inmediatamente la FASE 0.

No preguntes si debes continuar entre fases.
Borra esta línea y pega debajo la tarea o hiper-megaprompt que quieres que
Hermes ejecute.

Puedes cambiar este archivo más adelante para una nueva misión, pero antes
conviene mover o borrar el HANDOFF anterior y el contenido de .autoregen/state.
